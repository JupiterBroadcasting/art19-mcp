## 1. Setup & Auth

### Credentials

```bash
export ART19_API_TOKEN="your-token"
export ART19_API_CREDENTIAL="your-credential"
```

Auth header format:

```
Authorization: Token token="<ART19_API_TOKEN>", credential="<ART19_API_CREDENTIAL>"
```

### How the MCP Server Works

Single-file Babashka server (`art19_mcp.bb`, 1377 lines). Transport is **MCP Streamable HTTP**:

1. Client sends `initialize` → server creates session, returns `Mcp-Session-Id` header
1. Client sends `notifications/initialized` (notification, no response — 204)
1. All subsequent requests include `Mcp-Session-Id` header
1. Server validates session on every non-initialize request

### Session Lifecycle (via curl)

```
POST /mcp  {"jsonrpc":"2.0","method":"initialize"}
  ← 200  {"Mcp-Session-Id":"<uuid>", result: {protocolVersion, capabilities, serverInfo}}

POST /mcp  {"method":"notifications/initialized"}  [Mcp-Session-Id]
  ← 204   (no body)

POST /mcp  {"method":"tools/call", params: {name, arguments}}  [Mcp-Session-Id]
  ← 200   {result: {content: [{type: "text", text: "..."}], isError: bool}}
```

### Why curl instead of mcpc CLI

The mcpc bridge (`@apify/mcpc`) uses keepalive pings every ~30s. Our server did not implement the MCP `ping` method, returning `-32601 Method not found`. This caused:

- Bridge logs flooded with ping failure stack traces
- Sessions repeatedly marked as `disconnected`
- `mcpc @art19 --json tools-call list_series` timed out with no output

Direct curl worked reliably. **Ping handler was added during this session** (see §11).
